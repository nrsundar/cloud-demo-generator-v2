## Context

Today, the generator agent's "structure" is a 600-character system prompt instructing the model to return JSON matching a specific schema (`agentRoutes.ts:342-347`). The system relies on:

- The model honoring "Return ONLY valid JSON."
- A regex strip of markdown code fences (`agentRoutes.ts:353`).
- A single `JSON.parse` (`agentRoutes.ts:354`).
- A catch-all error handler returning a generic `ErrorCard` (`agentRoutes.ts:355-358`).

This is too fragile for production. Any model emission with a stray comma, a markdown header, or a non-conforming `GenNode` shape crashes the renderer in front of a customer.

The goal of P1.4 is to make invalid emissions **impossible to render** — not by adding more error handling, but by structurally constraining what the model can emit.

## Design

### Two layers of constraint

1. **Bedrock tool-use API** for tool calls within the loop (P1.2). The model's tool-call payloads are structurally guaranteed valid against the tool's `input_schema`.

2. **Server-side envelope validation** for the final response. The `complete` event payload (or the response body of the non-streaming endpoint) is validated against a Zod union of the 17 `GenNode` shapes plus the wrapping envelope.

### Envelope schema (`server/agent/envelope.ts`)

```ts
import { z } from "zod";

const GenNodeSchema = z.discriminatedUnion("type", [
  z.object({ type: z.literal("Markdown"), text: z.string() }),
  z.object({ type: z.literal("QuestionSingleSelect"), id: z.string(), label: z.string(),
             helper: z.string().optional(),
             options: z.array(z.object({ label: z.string(), value: z.string() })) }),
  // ... 15 more variants matching client/src/components/genui/types.ts
]);

const SpecSnapshotSchema = z.object({
  database: z.string(),
  extensions: z.array(z.string()),
  useCase: z.string(),
  industry: z.string().optional(),
  audience: z.string().optional(),
  durationMin: z.number().nullable().optional(),
  estCostHourly: z.string().optional(),
});

export const EnvelopeSchema = z.object({
  message: z.string(),
  components: z.array(GenNodeSchema),
  specSnapshot: SpecSnapshotSchema,
  phase: z.enum(["gathering", "generating", "complete", "error"]),
});

export type Envelope = z.infer<typeof EnvelopeSchema>;
```

The Zod union is the single source of truth and is generated from `client/src/components/genui/types.ts` via a small build step (`scripts/sync-gennode-schema.ts`) so the union cannot drift from the renderer's view of the world.

### Validation in the loop

```
final = bedrock.invoke(...)
parsed = EnvelopeSchema.safeParse(final.text)
if !parsed.success:
  appendStep(role='tool', toolResults=[{
    error: { kind: "envelope_validation",
             zodIssues: parsed.error.issues } }])
  if envelopeRetries < 1:
    envelopeRetries += 1
    continue                                  // single retry
  return ErrorEnvelope({ title: "Renderer mismatch",
                         message: "...", retryable: true })
```

**Single retry only.** The validation error is fed back to the model verbatim. If the second attempt also fails, the user gets an `ErrorCard` and the trace records both failures for debugging.

### What tool-use buys us

Tool calls happen *inside* the loop and use Bedrock's tool-use API. Bedrock guarantees:

- The `tool_use` block's `input` is valid JSON.
- The JSON conforms to the `input_schema` we provided.

This means the only place envelope validation can fail is the final assistant message — the place where the model decides what `components[]` to render. A well-tuned prompt + the catalog of tool calls in history makes this a much smaller surface than today's "model emits everything in one go."

### Discrepancy: 17 vs 18 GenNode types

`CONSTRAINTS.md` constraint 21 says "18 types defined in `components/genui/types.ts`." The actual file defines **17 types**:

```
Markdown, QuestionSingleSelect, QuestionMultiSelect, QuestionSlider, QuestionText,
DatabasePicker, ExtensionPicker, AudienceProfile, DemoSpecCard, InfraPreview,
SchemaPreview, CodePreview, ModuleList, CostEstimate, ProgressTimeline,
ConfirmationCard, ErrorCard
```

This needs reconciliation as part of P1.4 work. Either:

- Update constraint 21 to "17 types," or
- Add the 18th type intentionally (e.g. `RagCitation` for P3.1).

Track in [ADR-0010](../../decisions/0010-gennode-gated-process.md).

## Sequencing and dependencies

- **Before:** P1.2 (the tool-use API path is established there).
- **After:** P3.3 (renderer contract) builds an admin gallery that exercises every variant of `GenNodeSchema`.

## Exit criteria

1. `EnvelopeSchema.safeParse` succeeds on 100% of envelopes from a 200-prompt corpus (envelope validation is a non-issue at p50).
2. Single retry is exercised by injecting a deliberately malformed model response in test; second emission validates.
3. After two consecutive validation failures, the user sees `ErrorCard` and the trace contains both `tool_results` with `kind: "envelope_validation"`.
4. `scripts/sync-gennode-schema.ts` is wired into CI; an intentional drift between `types.ts` and the Zod union fails CI.
5. The 17-vs-18 discrepancy is resolved (either constraint updated or 18th type added with renderer support).

## Risks

| Risk | Mitigation |
|---|---|
| Zod discriminated unions and Bedrock tool-use have minor format mismatches | The in-house `zodToJsonSchema` (P1.2) is tested against every variant; CI fails on missing coverage. |
| The model wedges into a loop where the validation error confuses it | Cap at single retry; surface `ErrorCard`. Better to fail loudly than silently retry forever. |
| `client/src/components/genui/types.ts` and the Zod schema drift | Sync script in CI. |

## Out of scope

- Schema migrations for the existing `demo_requests.spec` JSON column (it is unstructured and not subject to envelope validation).
- Frontend "quarantine" rendering for partial envelopes (we either render fully or show `ErrorCard`).
