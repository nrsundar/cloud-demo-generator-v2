# P1.1 — Agent Loop with Persistent State

| | |
|---|---|
| **Status** | not started |
| **Effort** | 1 week |
| **Owner** | TBD |
| **Depends on** | none |
| **Blocks** | P1.2, P1.3, P2.1, P2.2 |

## Context

Today, `POST /api/generator/agent` (in `server/agentRoutes.ts:338`) is a one-shot Bedrock `InvokeModelCommand` call. The handler reads the request body, builds a system prompt, invokes Opus 4.6 once, parses the JSON response, and returns. There is no agent loop, no persistent state, no tool execution path — the model has to do everything in a single completion or fail.

This shape works for short conversations but is incompatible with everything Phase 1 builds on:

- **P1.2 (tool catalog)** needs a loop that can execute a tool, append the result to history, and call the model again.
- **P1.3 (streaming)** needs a server-side state machine that emits typed events as the loop progresses.
- **P2.1 (tracing)** needs every step of the loop to be persisted.
- **P2.2 (async)** needs sessions to survive HTTP disconnects.

The agent loop is the foundation. Until it lands, every other Phase 1 item is blocked.

## Design

### Schema additions (`shared/schema.ts`)

Two new Drizzle tables:

```ts
export const agentSessions = pgTable("agent_sessions", {
  id: serial("id").primaryKey(),
  userId: text("user_id").notNull(),               // Cognito sub
  userEmail: text("user_email").notNull(),         // denormalized for admin views
  phase: text("phase").notNull().default("gathering"),
  specSnapshot: json("spec_snapshot").$type<SpecSnapshot>(),
  lastEventId: integer("last_event_id").default(0),
  createdAt: timestamp("created_at").defaultNow().notNull(),
  updatedAt: timestamp("updated_at").defaultNow().notNull(),
});

export const agentSteps = pgTable("agent_steps", {
  id: serial("id").primaryKey(),
  sessionId: integer("session_id").references(() => agentSessions.id).notNull(),
  turnIndex: integer("turn_index").notNull(),
  role: text("role").notNull(),                    // 'user' | 'assistant' | 'tool'
  content: json("content"),                        // text or structured JSON
  toolCalls: json("tool_calls"),                   // [{ name, input, id }]
  toolResults: json("tool_results"),               // [{ id, output | error }]
  tokensIn: integer("tokens_in"),
  tokensOut: integer("tokens_out"),
  latencyMs: integer("latency_ms"),
  createdAt: timestamp("created_at").defaultNow().notNull(),
});
```

Indexes: `(sessionId, turnIndex)` for fast turn replay; `(userId, createdAt desc)` for "my recent sessions."

### Server reorganization

Today's logic in `server/agentRoutes.ts:338-359` is replaced with a thin handler that delegates to a loop core.

```
server/
  agentRoutes.ts                # thin: parses request, delegates
  agent/
    loop.ts                     # runTurn(sessionId, userMessage) — the core
    bedrock.ts                  # InvokeModelCommand wrapper, retry semantics
    budget.ts                   # loop budget enforcement
    sessions.ts                 # session load / persist
```

### Loop semantics

```
runTurn(sessionId, userMessage):
  session = sessionsRepo.load(sessionId)
  history = stepsRepo.loadHistory(sessionId)
  appendStep(session, role='user', content=userMessage)

  for iteration in 1..MAX_ITERATIONS:
    budget.check(session)                     // throws if exceeded
    response = bedrock.invoke(history, tools=toolCatalog.specs())
    appendStep(session, role='assistant', content=response.text,
               toolCalls=response.toolCalls,
               tokensIn, tokensOut, latencyMs)

    if response.toolCalls.length === 0:
      validated = validateEnvelope(response.text)
      if !validated.ok:
        appendStep(session, role='tool', toolResults=[{ error: validated.error }])
        continue                              // single retry per P1.4
      session.phase = validated.envelope.phase
      session.specSnapshot = validated.envelope.specSnapshot
      sessionsRepo.persist(session)
      return validated.envelope

    // execute tools (P1.2)
    results = await Promise.all(response.toolCalls.map(tc => toolCatalog.execute(tc, principal)))
    appendStep(session, role='tool', toolResults=results)

  throw BudgetExceededError("max iterations")
```

### Loop budget (`server/agent/budget.ts`)

Enforced server-side so a misbehaving model cannot run away:

- `MAX_ITERATIONS = 6`
- `MAX_TURN_LATENCY_MS = 90_000`
- `MAX_TOKENS_PER_TURN = 16_000`

Budget exceeded → emit an `ErrorCard` envelope and persist the session with `phase = "error"`. The user can start a new turn; previous turns are not lost.

### HTTP surface (unchanged externally for backwards compat)

```
POST /api/generator/agent
  body: { sessionId?: number, messages: AgentMessage[], specSnapshot?: SpecSnapshot }
  resp: { sessionId, message, components, specSnapshot, phase }
```

If `sessionId` is omitted, a new session is created. The frontend stores `sessionId` in `sessionStorage` (constraint 23) so subsequent turns reattach.

The streaming variant (`/api/generator/agent/stream`) is added in P1.3.

## Constraint compliance

| Constraint | How this complies |
|---|---|
| 5 — no new dependencies | Uses Drizzle, Zod, AWS SDK already in `package.json`. Zero additions. |
| 7 — Express + esbuild | Loop is in-house TypeScript; no LangChain, LangGraph, or runtime engine. |
| 8 — Drizzle + Neon | Both new tables defined in `shared/schema.ts` via Drizzle. No raw SQL. |
| 9 — Bedrock only | `bedrock.invoke()` wraps `InvokeModelCommand` against Opus 4.6. |
| 15 — auth on all routes | Handler stays behind `requireAuth`. Session ownership verified on load. |
| 17 — no secrets in frontend | Session state lives server-side; client only sees `sessionId`. |
| 20 — structured envelope | `validateEnvelope` enforces `{message, components, specSnapshot, phase}`. |
| 23 — `sessionStorage` persistence | Frontend stores `sessionId` only; server-side state authoritative. |

## Sequencing and dependencies

- **Before:** none.
- **After:** P1.2 plugs into the `tools` parameter of `bedrock.invoke()`. P1.3 turns `runTurn` into a generator function that yields events. P2.1 reads `agent_steps` for trace timelines. P2.2 turns `runTurn` into a worker job.

## Exit criteria

1. `agent_sessions` and `agent_steps` migrate cleanly on a fresh Neon database.
2. Existing `/generator` page works identically — no UX regression.
3. `agent_steps` has one row per model turn for every conversation, with non-null `tokensIn`, `tokensOut`, `latencyMs`.
4. Loop budget triggers a graceful `ErrorCard` envelope when exceeded (test: force `MAX_ITERATIONS = 1` and submit a tool-needing prompt).
5. Session resumption works across browser refreshes (test: refresh page mid-conversation; sessionStorage `sessionId` reattaches).
6. Parity test against today's Generator: 20 representative prompts produce equivalent envelopes.

## Risks

| Risk | Mitigation |
|---|---|
| Schema migration order matters across deploy + boot | `migrate.ts` handles ordering; verify `agent_sessions` exists before `agent_steps`. |
| `InvokeModelCommand` retry semantics differ from raw HTTP | `server/agent/bedrock.ts` centralizes retries; documented in code. |
| Long sessions accumulate large histories → token bloat | History windowing in `runTurn` (keep first turn + last N steps; older steps summarized). Out of scope for P1.1 — implement when first session exceeds 8K context. |
| In-memory `generatedZips` cache (`agentRoutes.ts:11`) is incompatible with multi-task ECS | Already a known issue; flag for separate fix. Not blocking. |

## Out of scope

- Tool execution (P1.2).
- Streaming (P1.3).
- Tracing UI (P2.1) — tables exist but the admin viewer is a separate item.
- Resume after browser disconnect mid-turn (P2.2).
