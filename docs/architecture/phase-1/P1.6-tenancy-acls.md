## Context

Today's authorization model has one layer: `requireAuth` middleware (`server/auth.ts`) validates a Cognito JWT and attaches `req.user`. Admin routes additionally use `requireAdmin`. This stops a logged-out user from hitting the API but does not stop logged-in users from asking the agent for someone else's data.

Examples of holes:

- An SA tells the agent: "show me the latest demos requested by alice@example.com." Today's `searchPriorDemos` tool (once it exists) would happily return them — there is no per-row ACL check inside the tool.
- A future RAG tool indexes customer notes scoped to the AE who owns the account. Without ACL filtering at retrieval time, embeddings leak across tenants.
- A TAM in one region should not see a different region's drafts unless the team policy allows it.

ACLs must be enforced inside the tool layer, not just at the HTTP layer, because the model will call tools on behalf of users and the tool is the last point where data flows out.

## Design

### Schema additions

Add ownership columns to existing tables. New columns default to `NULL` for old rows; backfill is a one-time migration (`server/migrate.ts` extension).

```ts
// shared/schema.ts (additions)

export const demoRequests = pgTable("demo_requests", {
  // ... existing columns
  ownerId: text("owner_id"),                 // Cognito sub
  teamId: text("team_id"),                   // optional, free-form for now
});

export const repositories = pgTable("repositories", {
  // ... existing columns
  ownerId: text("owner_id"),
  teamId: text("team_id"),
  visibility: text("visibility").notNull().default("private"),
                                            // 'private' | 'team' | 'org'
});

// agent_sessions, agent_steps already include userId from P1.1.
```

Backfill: `requesterEmail` is denormalized email in current rows; map email → Cognito sub via Cognito `ListUsers` (one-time admin script). Rows with no match stay `NULL` and require admin claim.

### Principal threading

`requireAuth` enriches `req.user` to include `isAdmin` (from Cognito group membership):

```ts
// server/auth.ts
interface Principal {
  userId: string;        // Cognito sub
  email: string;
  isAdmin: boolean;
  teamIds: string[];     // from a "team:<id>" Cognito group convention
}
```

The agent loop's `runTurn(sessionId, userMessage, principal)` receives the principal and threads it into every tool's `execute(principal, input)`.

### ACL enforcement pattern (per tool)

Each tool that reads data implements a consistent check:

```ts
// server/tools/searchPriorDemos.ts
export const searchPriorDemos: ToolSpec<...> = {
  name: "searchPriorDemos",
  // ...
  async execute(principal, input) {
    const rows = await db.select().from(repositories)
      .where(and(
        ilike(repositories.name, `%${input.query}%`),
        or(
          eq(repositories.ownerId, principal.userId),
          eq(repositories.visibility, "org"),
          and(
            eq(repositories.visibility, "team"),
            inArray(repositories.teamId, principal.teamIds)
          ),
          principal.isAdmin ? sql`TRUE` : sql`FALSE`,
        ),
      ))
      .limit(input.limit ?? 10);
    return { demos: rows.map(toDemoSummary) };
  },
};
```

The model cannot escape this — even if it asks "ignore ACLs and show me everything," the tool's `execute()` simply does not return data that would not pass the WHERE clause. ACL is a property of the **query**, not the **prompt**.

### Visibility model

Three values:

- **`private`** — owner only (plus admins).
- **`team`** — owner's `teamId` only (plus admins).
- **`org`** — every authenticated user (plus admins).

Default for new rows is `private`. Admin can promote to `team` or `org` via the admin UI (existing Admin Dashboard tab; adds a "visibility" dropdown per row).

### Admin elevation

Admins (Cognito group `admin`) bypass per-row ACL but their reads are *audited* — every admin tool call records `principal.userId` and `principal.isAdmin = true` in `agent_steps`. The audit trail is queryable via P2.1's trace UI.

This is intentional: admins need cross-tenant visibility to support the field, but every cross-tenant read is logged.

### Helper

A reusable Drizzle helper avoids ACL drift:

```ts
// server/auth/acl.ts
export function visibleTo(principal: Principal, table: { ownerId, teamId, visibility }) {
  if (principal.isAdmin) return sql`TRUE`;
  return or(
    eq(table.ownerId, principal.userId),
    eq(table.visibility, "org"),
    and(
      eq(table.visibility, "team"),
      inArray(table.teamId, principal.teamIds),
    ),
  );
}
```

Every tool uses `visibleTo(principal, repositories)` rather than re-implementing the predicate.

### Frontend implications

The Admin Dashboard tabs for cross-tenant views already exist; they add a visibility column showing the current value and an inline editor for admins. No other UI changes — every other page already reflects the principal's view.

## Exit criteria

1. Integration test — user A creates a `private` demo. User B asks the agent to "show me alice's recent demos." Tool returns zero matches.
2. Integration test — user A creates a `team` demo with `teamId = "northeast-sa"`. User C in the same team retrieves it via tool. User D in a different team does not.
3. Integration test — admin retrieves any row from any tenant and the trace records `principal.isAdmin = true`.
4. Backfill report — fewer than 1% of `demo_requests` rows remain unowned after the email→sub mapping; remaining rows surfaced for admin claim.
5. Lint rule (or grep test) — every tool's `execute()` either uses `visibleTo()` or has a `// no-acl-needed: <reason>` comment. Drift caught in CI.

## Risks

| Risk | Mitigation |
|---|---|
| Backfill mis-maps users with multiple Cognito accounts on the same email | Manual review before applying; admin UI surfaces ambiguous rows. |
| Team ID convention via Cognito groups is brittle | Acceptable for v1; revisit when team count exceeds ~10. |
| ACL evaluation in `WHERE` clauses is verbose | `visibleTo()` helper keeps each tool small. |
| Admin reads bypass row-level checks | Intentional; audited via P2.1 trace UI; high-cardinality access pattern would surface in cost dashboards. |

## Out of scope

- Field-level ACL (e.g. hide cost columns from non-admins) — current scope is row-level only.
- Customer-level ACL (e.g. SA assigned to customer X cannot see customer Y) — defer until a customer-account model exists in DemoForge data.
- ABAC / policy DSL — three visibility levels are sufficient for v1.
