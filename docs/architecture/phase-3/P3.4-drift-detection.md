## Context

Stochastic systems drift silently. A model update on the Bedrock side, a new prompt version, a tool that quietly returns slightly different results — none of these necessarily fail eval, but they shift the distribution of outputs over time. By the time the field notices, weeks of low-quality demos have shipped.

P3.4 is a small but valuable safety net. A daily cron compares recent production behavior to a 30-day baseline and surfaces anomalies for an admin to review.

## Design

### What we monitor

| Metric | Source | Drift threshold |
|---|---|---|
| Phase outcome distribution | `agent_traces.status` rollup over 7 days vs. 30-day baseline | > 15% relative change in `error` rate |
| Tool error rate | `agent_spans` where `kind='tool'` AND `error IS NOT NULL` | > 25% relative change |
| Avg tokens per turn (Opus) | `agent_traces.totalTokensIn + Out` mean | > 20% relative change |
| Cost per conversation | `agent_traces.estCostUsd` mean | > 30% relative change |
| Eval tier 2 score | `eval_runs.scoreSummary.tier2` 7-day vs. 30-day | > 5 absolute points |
| Retrieval recall@10 (post-P3.1) | trace-level retrieval span counts | > 10% relative change |

Thresholds are starting points — tune on observed variance.

### Implementation

A daily job (existing ECS task, `setInterval` running once per 24 hours) computes each metric and inserts a row into a new table:

```ts
// shared/schema.ts

export const driftReports = pgTable("drift_reports", {
  id: serial("id").primaryKey(),
  generatedAt: timestamp("generated_at").defaultNow().notNull(),
  metric: text("metric").notNull(),
  recentValue: text("recent_value").notNull(),
  baselineValue: text("baseline_value").notNull(),
  relativeChange: text("relative_change").notNull(),
  severity: text("severity").notNull(),       // 'info' | 'warn' | 'alarm'
  details: json("details"),
});
```

Severity:

- **info** — within threshold; recorded for trend.
- **warn** — exceeded threshold; visible in admin UI.
- **alarm** — exceeded threshold by 2x; SNS notification (where SNS topic exists; v1 is admin-UI-only).

### Admin UI

New tab under Admin Dashboard, "Drift":

- **Active alerts** — `warn` and `alarm` rows from the last 7 days.
- **Trend charts** — each metric over the last 90 days (inline SVG line, no library).
- **Acknowledge** — admin can mark an alert as acknowledged with a note. Acknowledged alerts hide from the active list but remain in history.

Uses existing CSS classes; no new design tokens.

### Test path

A `POST /api/admin/drift/simulate` endpoint (admin-only) inserts a synthetic drift report so the admin UI is exercisable without waiting for real drift.

```
POST /api/admin/drift/simulate
  body: { metric: "phase_error_rate", relativeChange: "+0.3" }
```

Used in P3.4 validation tests.

## Sequencing and dependencies

- **Before:** P2.1 (traces are the source for most metrics), P2.4 (eval-related metrics).
- **After:** none.

## Exit criteria

1. Daily job runs successfully for 7 consecutive days; one row per metric per day in `drift_reports`.
2. Simulated drift via `/api/admin/drift/simulate` surfaces in admin UI within 1 minute.
3. Each threshold is documented in this file and tunable via a constants file (no DB migration needed to adjust).
4. False-positive rate review after 30 days: ≤ 1 false alarm per week. Tighten thresholds if higher.

## Risks

| Risk | Mitigation |
|---|---|
| 30-day rolling baselines are noisy when traffic is low | Switch to a longer window (e.g. 90 days) for low-traffic metrics; documented in tuning notes. |
| Alarms become noise; team starts ignoring them | Acknowledge flow + monthly review; tune thresholds to keep alarms rare and meaningful. |
| Baseline drifts naturally over time and "drift" becomes the norm | Quarterly baseline reset with explicit decision log. |
| ETL on `agent_spans` becomes expensive at scale | Materialize daily summaries into a `agent_traces_daily` rollup if span-scan latency exceeds 30 seconds. |

## Out of scope

- Real-time alerting (we run daily; revisit if a customer-facing incident demands sooner detection).
- ML-based anomaly detection. Simple thresholds are sufficient for v1; revisit when we have 6+ months of metric history.
- Automatic remediation (no auto-rollback of prompts; admin reviews and decides).
