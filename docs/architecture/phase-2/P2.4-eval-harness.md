# P2.4 — Eval Harness in CI

| | |
|---|---|
| **Status** | not started |
| **Effort** | 1.5 weeks |
| **Owner** | TBD |
| **Depends on** | P1.2 (tool catalog), P2.1 (tracing — for scoring), P2.3 (caching — eval needs to be aware of cache state) |
| **Blocks** | none — but every Phase 3 prompt change should ride this gate |

## Context

Without an eval harness, every prompt or model change is a vibes question: "does this feel better?" With one, it is a measurable one: "does this score higher on a stable test set?"

The harness is also the gate that prevents silent regressions. It must be cheap enough to run on every MR (≤ 5 minutes) and thorough enough nightly to catch slow drift.

## Design

### Test corpus

JSONL fixtures versioned in the repo:

```
tests/evals/
  README.md
  fixtures/
    01-pgvector-fintech.jsonl
    02-postgis-realestate.jsonl
    03-pgroute-logistics.jsonl
    04-pgvector-healthcare.jsonl
    ...
  rubrics/
    spec-completeness.md
    component-coverage.md
    code-quality.md
  judges/
    spec-judge-prompt.md
    code-judge-prompt.md
  run.ts                         // entry point
  score.ts                       // scoring logic
  report.ts                      // output formatting
```

Initial target: **30 fixtures** spanning the three extensions × five industries × two complexities. Grow as new bugs surface — every reported bug becomes a fixture.

Fixture shape:

```jsonl
{
  "id": "01-pgvector-fintech-fraud",
  "prompt": "I need a demo for a fintech customer doing fraud detection with embeddings.",
  "expectedPhase": "generating",
  "expectedSpec": {
    "database": "PostgreSQL",
    "extensions": ["pgvector"],
    "useCase": "fraud detection",
    "industry": "fintech"
  },
  "expectedComponents": ["AudienceProfile", "InfraPreview", "SchemaPreview"],
  "expectedArtifacts": {
    "cfn": { "hasResource": ["AWS::RDS::DBInstance"], "noResource": ["AWS::S3::Bucket@@PublicRead"] },
    "schema": { "hasTable": ["transactions", "accounts"], "minColumns": 4 }
  },
  "rubrics": ["spec-completeness", "component-coverage"],
  "tags": ["pgvector", "fintech", "complexity:medium"]
}
```

### Scoring tiers

Three tiers:

1. **Deterministic checks** (cheap, fast): exact-match on `expectedSpec.*`, presence of `expectedComponents`, structural checks on `expectedArtifacts`. ~30ms per fixture.
2. **Rubric-based heuristics** (medium): regex patterns + token counts + light semantic checks. ~200ms per fixture.
3. **LLM-as-judge** (expensive): Bedrock call to a model evaluating the output against a rubric prompt. ~5s per fixture.

CI runs tier 1 + tier 2 on every MR (the "fast suite"). Nightly cron runs all three (the "full suite") and posts deltas.

### LLM-as-judge

Important properties:

- The judge model is *different* from the model being evaluated. Same-model evaluation is biased toward its own outputs. Today this means the judge is also Opus 4.6 (single-model constraint per [ADR-0011](../../decisions/0011-multi-model-routing.md)) — note this in eval reports as a known bias.
- Judge prompts live in `tests/evals/judges/*.md` and are versioned alongside fixtures.
- Judge output is structured (Bedrock tool-use schema) so scoring is mechanical: `{ score: number, rationale: string }`.

If [ADR-0011](../../decisions/0011-multi-model-routing.md) resolves to allow Sonnet, switch the judge to Sonnet — different model family eliminates the same-model bias.

### Run mechanics

```
tests/evals/run.ts
  - Spins up an in-process agent with caching disabled (eval determinism).
  - For each fixture:
    - Sends the prompt through the agent loop (P1.1 + P1.2).
    - Captures the final envelope and the trace.
    - Runs scorers.
    - Records (fixtureId, tier, score, latency, costUsd, traceId) to eval_runs table.
  - Aggregates per tier and per tag.
  - Compares against the latest baseline; prints a delta.
```

Eval runs themselves are traced (P2.1), so we can debug eval failures using the trace UI.

### Schema additions

```ts
export const evalRuns = pgTable("eval_runs", {
  id: serial("id").primaryKey(),
  ranAt: timestamp("ran_at").defaultNow().notNull(),
  ranBy: text("ran_by").notNull(),                  // 'ci' | 'nightly' | <user-email>
  commitSha: text("commit_sha"),
  branchName: text("branch_name"),
  suite: text("suite").notNull(),                   // 'fast' | 'full'
  totalFixtures: integer("total_fixtures").notNull(),
  passedFixtures: integer("passed_fixtures").notNull(),
  scoreSummary: json("score_summary"),              // { tier1, tier2, tier3, byTag }
  totalCostUsd: text("total_cost_usd"),
  totalLatencyMs: integer("total_latency_ms"),
});

export const evalResults = pgTable("eval_results", {
  id: serial("id").primaryKey(),
  runId: integer("run_id").references(() => evalRuns.id).notNull(),
  fixtureId: text("fixture_id").notNull(),
  tier: text("tier").notNull(),                     // '1' | '2' | '3'
  score: integer("score").notNull(),                // 0-100
  passed: text("passed").notNull(),                 // 'true' | 'false'
  latencyMs: integer("latency_ms"),
  costUsd: text("cost_usd"),
  traceId: integer("trace_id").references(() => agentTraces.id),
  rationale: text("rationale"),
});
```

### CI integration

GitLab CI job `.gitlab-ci.yml` (added if not present):

```yaml
eval-fast:
  stage: test
  image: node:18
  script:
    - npm ci
    - npm run eval:fast
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
  artifacts:
    when: always
    reports:
      junit: tests/evals/report.xml
```

Fail the pipeline if any fixture in tier 1 fails (deterministic regression) or if tier 2 average score drops by more than 5 points vs. the latest `main` baseline.

### Nightly job

A second GitLab schedule runs the full suite (including LLM-as-judge) at midnight UTC. Results are inserted into `eval_runs` and visible in the admin "Evals" tab (added as part of P2.4).

### Admin UI

New tab in Admin Dashboard, "Evals":

- **Run list** — sortable by date, branch, score.
- **Run detail** — per-fixture results with link to trace.
- **Trend view** — score over time per tier, per tag (line chart, inline SVG).

Uses existing CSS classes (no new tokens, no chart library, per constraints 1–4).

### Baseline management

Latest `main` run becomes the baseline automatically. A `tests/evals/baselines/` directory holds frozen baselines for major releases (manual `npm run eval:freeze`).

Regressions block MRs by default. The MR description can include `eval-override: <reason>` to allow merge despite a regression — recorded for audit, requires `phase-1` or `architecture` MR label.

## Constraint compliance

| Constraint | How this complies |
|---|---|
| 5 — no new dependencies | Uses existing `tsx`, Zod, AWS SDK. |
| 8 — Drizzle + Neon | Eval results in two new Drizzle tables. |
| 9 — Bedrock only | LLM-as-judge uses Bedrock. |
| 16 — admin check | Eval admin UI requires admin. |

## Sequencing and dependencies

- **Before:** P1.2 (the agent must be in good shape to produce stable evaluable output), P2.1 (eval results link to traces), P2.3 (cache state matters for determinism).
- **After:** Every Phase 3 prompt change rides this gate.

## Exit criteria

1. 30+ fixtures in `tests/evals/fixtures/`.
2. Fast suite runs in ≤ 5 minutes; nightly suite in ≤ 30 minutes.
3. CI gate active: an intentional prompt regression fails the pipeline.
4. Admin Evals tab renders the latest run with per-fixture details and trace links.
5. Three weeks of nightly data show stable baselines (variance ≤ 3 points on tier 2).
6. Cost of nightly suite is ≤ $5 per night (constraint check via P2.1 cost rollup).

## Risks

| Risk | Mitigation |
|---|---|
| Fixtures grow stale as the system evolves | Quarterly fixture review + bug-driven fixture additions. |
| LLM-as-judge has same-model bias | Documented; switch to Sonnet judge once ADR-0011 resolves. |
| Eval runs are flaky due to model nondeterminism | Use temperature=0 where supported; multi-sample tier 3 (run 3x, average). |
| Eval costs exceed budget | Track in P2.1 cost rollup; alarm at $10/night. |
| Eval gate becomes a checkpoint people route around | Only `architecture` MRs can override; logged in the MR description. |

## Out of scope

- Continuous-evaluation in production (sampling live conversations and scoring) — defer to Phase 3+.
- Human evaluation loop (SAs rating results) — defer; the rubrics handle most of what humans would.
- A/B testing infrastructure — defer until we have a second model to compare to (gated on ADR-0011).
