## Context

Generation runs that take 60–120 seconds can fail in many ways: SA closes the laptop, Wi-Fi drops, ECS task is replaced, browser tab freezes. Today, all of those throw away in-progress work.

The fix is to detach generation from the HTTP request lifecycle. The agent endpoint becomes a job submission; a worker runs the agent loop; the SSE stream is a *view* on the running job, not the job itself. The SA can disconnect, reconnect, leave for a meeting, come back — the job runs to completion either way.

[ADR-0002](../../decisions/0002-async-via-postgres-queue.md) records the decision to use a Postgres-backed queue rather than Temporal/BullMQ/Redis. At field-tool scale this is sufficient, requires zero new infrastructure, and uses the database we already have.

## Design

### Schema additions

```ts
// shared/schema.ts

export const agentJobs = pgTable("agent_jobs", {
  id: serial("id").primaryKey(),
  sessionId: integer("session_id").references(() => agentSessions.id).notNull(),
  turnIndex: integer("turn_index").notNull(),
  state: text("state").notNull().default("ready"),
                                                    // 'ready' | 'leased' | 'done' | 'failed' | 'cancelled'
  attempts: integer("attempts").notNull().default(0),
  maxAttempts: integer("max_attempts").notNull().default(3),
  idempotencyKey: text("idempotency_key").notNull().unique(),
  payload: json("payload").notNull(),               // input to runTurn
  result: json("result"),                           // final envelope, on success
  lastError: json("last_error"),
  leaseUntil: timestamp("lease_until"),
  workerId: text("worker_id"),                      // ECS task identifier
  createdAt: timestamp("created_at").defaultNow().notNull(),
  updatedAt: timestamp("updated_at").defaultNow().notNull(),
});
```

Indexes:

- `(state, leaseUntil)` for the polling query.
- `(sessionId, turnIndex)` for the resume query.
- Unique `(idempotencyKey)`.

### Worker loop

Same ECS task, separate event loop:

```
// server/agent/worker.ts
function startWorker() {
  const workerId = `${os.hostname()}-${process.pid}`;
  setInterval(async () => {
    const job = await leaseNextJob(workerId, leaseDurationMs = 60_000);
    if (!job) return;
    try {
      const result = await runTurn(job.payload, ...);
      await markJobDone(job.id, result);
    } catch (err) {
      await markJobFailed(job.id, err);
    }
  }, 1_000);
}
```

`leaseNextJob` is one atomic SQL update:

```sql
UPDATE agent_jobs
SET state = 'leased',
    workerId = $1,
    leaseUntil = now() + interval '60 seconds',
    attempts = attempts + 1,
    updatedAt = now()
WHERE id = (
  SELECT id FROM agent_jobs
  WHERE state = 'ready' OR (state = 'leased' AND leaseUntil < now())
  ORDER BY createdAt
  LIMIT 1
  FOR UPDATE SKIP LOCKED
)
RETURNING *;
```

`FOR UPDATE SKIP LOCKED` is a Postgres feature that lets multiple workers safely race for jobs without manual coordination.

(Drizzle compatibility: `FOR UPDATE SKIP LOCKED` is supported via Drizzle's `.for("update", { skipLocked: true })` builder. If a future Drizzle release drops this, fall back to `db.execute(sql\`...\`)` which is still inside Drizzle's API surface and complies with constraint 8 — see also [ADR-0002](../../decisions/0002-async-via-postgres-queue.md).)

### Endpoint changes

```
POST /api/generator/agent/start
  body: { sessionId?, messages, specSnapshot? }
  resp: { sessionId, requestId, streamUrl }

GET /api/generator/agent/stream?requestId=<id>&lastEventId=<n>
  → same SSE protocol as P1.3 but keyed by requestId, not sessionId
```

The legacy `POST /api/generator/agent` is kept as a thin wrapper — it submits a job, polls until `state = 'done'`, and returns the result. This preserves backwards compatibility for any non-streaming clients.

### Resume from My Requests

Today's My Requests page (`client/src/pages/my-requests.tsx`) gets a "Resume" action on any request whose latest job is in `state = 'leased' | 'ready'`:

- Click → navigate to `/generator?sessionId=<id>` and reattach the SSE stream via `streamUrl`.
- If the job has completed during the SA's absence, the page shows the final envelope immediately.

### Idempotency

`idempotencyKey` is `sha256(sessionId + turnIndex + serializeMessages(messages))`. A duplicate `start` call with the same key returns the existing job's `requestId` instead of creating a new one. This handles the common case where the SA double-clicks "Generate."

### Per-step retries (later refinement)

For v1, a job retry restarts the turn from scratch. The optimization — retry from the failed *step* — is deferred to v1.1. The schema already supports it (`agent_steps.turnIndex` lets us resume from the last successful step), but the loop refactor to be checkpointable is non-trivial.

### Worker concurrency

One ECS task = one worker = one job at a time, for v1. Field-tool scale (estimated 5–20 concurrent SAs) does not need more. Scale knobs:

1. ECS desired count (cheap, immediate).
2. Multiple worker loops per ECS task (one CPU per worker; future once we observe needing it).

If the ready queue depth exceeds 10 for more than 60 seconds, bump ECS desired count via auto-scaling rule. Document as part of P2.2 runbook.

### Cleanup

Daily job:

- Delete `done` jobs older than 30 days.
- Delete `failed` jobs older than 90 days (longer for debugging).
- Cancel `leased` jobs whose `leaseUntil` is more than 1 hour past (likely zombie).

## Sequencing and dependencies

- **Before:** P1.1 (sessions), P1.2 (tools), P1.3 (SSE), P2.1 (traces — for debugging async failures).
- **After:** none.

## Exit criteria

1. Submit a turn, kill the browser, return 5 minutes later via My Requests → see the completed result.
2. Two SAs submit jobs simultaneously; both run to completion without `idempotencyKey` collision.
3. Force-kill a worker mid-job; another worker leases and completes within 90 seconds (lease expiry).
4. Submit the same turn twice (double-click) — second submission returns the existing `requestId`, not a new job.
5. Queue depth metric (count of `ready` rows) is exported via `/api/admin/queue-depth` and visible in the admin dashboard.

## Risks

| Risk | Mitigation |
|---|---|
| Postgres `FOR UPDATE SKIP LOCKED` performance under load | At our scale not an issue; revisit if `agent_jobs` exceeds 100K active rows. |
| Worker process dies without releasing lease | Lease expiry (60s) + zombie cleanup (1h) recover automatically. |
| Long-running tools time out under lease | Lease can be extended via `UPDATE agent_jobs SET leaseUntil = leaseUntil + interval '60s'` mid-execution. |
| SSE stream attaches before worker has emitted any events | Stream returns "no events yet" status; client retries every 500ms until first event. |
| ADR-0002 revisited: external orchestrator becomes necessary | Documented exit conditions in ADR-0002; review at 100 SAs / week. |

## Out of scope

- Per-step checkpoint retry (v1.1).
- Cross-region failover (we are single-region).
- Worker autoscaling beyond ECS desired count manual bump.
- External orchestrator (Temporal / Step Functions).
