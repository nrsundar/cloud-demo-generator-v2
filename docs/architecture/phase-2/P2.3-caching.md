# P2.3 — Multi-Layer Caching

| | |
|---|---|
| **Status** | not started |
| **Effort** | 3–4 days |
| **Owner** | TBD |
| **Depends on** | P1.2 (tool catalog), P2.1 (cost accounting tables to measure savings) |
| **Blocks** | P3.1 (RAG depends on the embedding cache) |

## Context

GenAI calls are slow and expensive. Three levels of caching apply:

1. **Prompt caching** — the system prompt and tool catalog are stable across turns within a session and stable across sessions for hours. Bedrock prompt caching (where available) cuts input tokens by ~70–90%.
2. **Tool result caching** — pricing math, schema templates, extension catalogs do not change every minute. A tool result cache eliminates repeated work.
3. **Embedding caching** — once a document is embedded, it should never be embedded again. Required for P3.1.

P2.3 builds all three. Expected impact: per-conversation Bedrock cost cut by ≥ 50%, p50 latency cut by ≥ 30%.

## Design

### Layer 1 — Bedrock prompt caching

Bedrock supports `cache_control` markers on stable prompt segments. Configuration only — no code change to the model invocation, only to how the system prompt is structured.

```ts
// before
const system = SYSTEM_PROMPT;

// after
const system = [
  { type: "text", text: SYSTEM_PROMPT, cache_control: { type: "ephemeral" } },
  { type: "text", text: TOOL_CATALOG_DESCRIPTION, cache_control: { type: "ephemeral" } },
];
```

The first call within a 5-minute window populates the cache; subsequent calls hit it. Cache hit and miss are both reported in `usage.cache_creation_input_tokens` / `usage.cache_read_input_tokens`. Both go into `agent_spans.cacheHit` for observability.

**Risk:** Bedrock prompt caching availability for Opus 4.6 in `us-east-2` is not guaranteed at any given time. Verify before relying on it; fall back to layer 1b if missing.

### Layer 1b — In-app prompt cache (fallback)

If Bedrock prompt caching is unavailable, an in-app cache stores `(systemPromptHash, toolCatalogHash) → completion` for short-lived (5-minute) hits when the *entire* input is identical. This is rare in conversation but happens on duplicate clicks; useful but small win compared to layer 1.

### Layer 2 — Tool result cache

```ts
// shared/schema.ts

export const toolResultCache = pgTable("tool_result_cache", {
  id: serial("id").primaryKey(),
  toolName: text("tool_name").notNull(),
  inputHash: text("input_hash").notNull(),
  result: json("result").notNull(),
  createdAt: timestamp("created_at").defaultNow().notNull(),
  expiresAt: timestamp("expires_at").notNull(),
  hitCount: integer("hit_count").notNull().default(0),
});
```

Index: unique `(toolName, inputHash)`.

`inputHash` is `sha256(toolName + canonicalize(input))`. Canonicalization = sorted-key JSON serialization, normalized whitespace, lowercased string fields where semantics permit (per-tool decision).

Each tool declares its TTL:

| Tool | TTL | Rationale |
|---|---|---|
| `lookupExtensions` | 7 days | Static catalog |
| `searchPriorDemos` | 1 hour | Catalog grows; freshness matters but not minute-by-minute |
| `estimateInfraCost` | 24 hours | AWS pricing changes are infrequent and acceptable to lag a day |
| `generateCFTemplate` | 24 hours | Same input → same output by construction |
| `generateSchema` | 24 hours | Deterministic given input |
| `generateAppCode` | 24 hours | Deterministic given input |
| `generateModules` | 7 days | Module text is stable |
| `lookupCustomerAccount` | 30 minutes | Customer notes change |

Cleanup job (1/day) removes expired rows.

### ACL note for tool result cache

Tools whose output depends on the **principal** (e.g. anything in P1.6 that filters by `ownerId`) must hash the principal into `inputHash`. Otherwise user A's cached result leaks to user B.

Implementation: tools mark themselves as `principalSensitive = true` in the spec; the cache wrapper hashes `principal.userId` into the key.

### Layer 3 — Embedding cache

```ts
// shared/schema.ts

export const embeddingCache = pgTable("embedding_cache", {
  id: serial("id").primaryKey(),
  textHash: text("text_hash").notNull(),                  // sha256(text)
  modelId: text("model_id").notNull(),                    // e.g. 'amazon.titan-embed-text-v2'
  embedding: text("embedding").notNull(),                 // base64-encoded float32 vector
  createdAt: timestamp("created_at").defaultNow().notNull(),
});
```

Index: unique `(textHash, modelId)`.

(In Phase 3, when pgvector is added per [ADR-0005](../../decisions/0005-pgvector-on-neon.md), the `embedding` column becomes a `vector(N)` column directly.)

Embeddings never expire — text + model ID = deterministic embedding. The cache is monotonic, append-only.

### Cache wrapper integration

In `server/tools/index.ts`, the registry wraps each tool's `execute()` with:

```ts
async function withCache(spec, principal, input) {
  if (!spec.cacheTtlSec) return spec.execute(principal, input);
  const key = sha256(spec.name + canonicalize(input) + (spec.principalSensitive ? principal.userId : ""));
  const hit = await cacheRepo.get(spec.name, key);
  if (hit) {
    metrics.cacheHit(spec.name);
    return hit;
  }
  const result = await spec.execute(principal, input);
  await cacheRepo.put(spec.name, key, result, spec.cacheTtlSec);
  return result;
}
```

The cache hit/miss is recorded in `agent_spans.cacheHit` (P2.1).

### Failure modes

- **Cache write fails:** log and continue. The result is returned; the cache is best-effort.
- **Cache read fails (DB error):** treat as miss; log and continue.
- **Stale cache poisoning:** every entry has `expiresAt`; never returned past expiry. Manual purge via admin endpoint `POST /api/admin/cache/purge?tool=`.

## Sequencing and dependencies

- **Before:** P1.2 (tools must exist before their results can be cached), P2.1 (cost spans needed to measure cache effectiveness).
- **After:** P3.1 (RAG fills the embedding cache).

## Exit criteria

1. On the eval set (after P2.4 lands), average per-conversation Bedrock cost decreases by ≥ 50% with all three layers active.
2. Tool result cache hit rate ≥ 30% on representative production traffic over 7 days.
3. Embedding cache hit rate ≥ 95% after one week of P3.1 use.
4. Principal-sensitive tools never return cross-user cached results in a fuzzed test (user A and user B with same input get correctly different results).
5. Manual cache purge endpoint works and is admin-gated.

## Risks

| Risk | Mitigation |
|---|---|
| Bedrock prompt caching unavailable for Opus 4.6 in us-east-2 | Layer 1b fallback; no functional impact, only cost. |
| Cache key drift between code and tests | Single canonicalization function shared by both. |
| Tool result cache returns stale data after a real-world change (e.g. EC2 pricing update) | TTLs are short for volatile data; admin purge endpoint as escape hatch. |
| Principal-sensitive tools forget to opt in | Lint rule: every tool must explicitly set `principalSensitive: true | false`. |
| Embedding cache row growth | Monotonic, but adding `vector(1536)` column means ~6 KB per row. Estimate ≤ 5M rows over 2 years; ~30 GB. Acceptable on Neon; alarm at 80%. |

## Out of scope

- HTTP-layer caching (CloudFront already caches the static frontend; the API explicitly disables caching).
- Cross-tenant shared cache for non-sensitive tools (already the default; we just don't call it out).
- Distributed cache (Redis / ElastiCache) — not needed at our scale; revisit if Neon round-trip becomes a bottleneck.
